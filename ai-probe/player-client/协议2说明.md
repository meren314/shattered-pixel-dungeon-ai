# 可靠协议 2

1. 客户端保存已确认基线和一个待交付批次，输出前先持久化。未确认时重放同一批次，不提前推进事件或地图游标。`ack` 或 `--seen` 确认后才提交基线。
2. `reset` 从空状态重建；普通 patch 使用 set/delete/items。字段缺失、null 和删除不同。`protocol_v2.py` 负责解码、差分、合并和摘要校验，不能手工猜测压缩标记。
3. `valid=false` 不用于新动作；忙碌批次保留旧业务状态。`view` 是已确认的本地视图。模型失去上下文时通过 `brief` 或 `resync` 恢复。
4. 服务端 `/frame` 在同一渲染回调内采集状态、事件和地图，并检查采样期间的版本变化。这是稳定性检查，不是全世界事务锁。动作入口仍重新检查观测版本和可操作状态。
5. action/start/load 提交前保存 request_id 和请求体。服务端同编号同内容只返回原回执；编号冲突拒绝。结果未知、超时或进程变化时只查询 `resume`，不自动重发。
6. accepted 表示接受请求，completed 表示恢复到可观察状态，不保证命中或预期交互成功。`interact-at` 另用公开结果证据区分 completed、not_completed、awaiting_user_choice 和 interrupted。
7. 一旦产生未知结果，禁止继续改变游戏。无服务端记录也不能证明动作未执行。`resolve` 仅供真实人类审核后登记理由；AI 不得冒充人工解除。
8. 地图、可见说明和背包都参与批次与确认。首次和变化说明自动进入 knowledge.text；未变化内容保留不重发。map_items 是游戏地图仍显示的已见物品堆，不是隐藏物品扫描。
9. goto 在已探索地图规划，逐步核对可见路线；interact-at 接近后再复核目标并执行明确意图。新危险、伤害、重要变化和未知请求会停止。恢复请求不会自动续做整个意图。
10. brief 只是上下文替换提议；外部环境实际替换历史后才 ack-context。记录 usage 需要真实单次模型用量，输出字符数不能当 token 或订阅额度。
11. 本协议依赖本地磁盘持久化与单消费者。损坏或丢失日志、外部手动切换游戏等情况可能需要人工复核；不能承诺跨所有故障的严格 exactly-once。
